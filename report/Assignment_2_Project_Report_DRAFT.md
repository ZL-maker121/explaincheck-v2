# ExplainCheck: A Human-Centred AI Explanation and Feedback Prototype

Counted words (abstract + main report): 1260; abstract: 200; main report: 1060.

## Abstract

ExplainCheck is an original, browser-based prototype exploring how people assess AI-assisted decisions. The problem is that an explanation or numerical score may appear useful without helping a person detect an incorrect recommendation. The prototype narrows this question to fictional customer-support ticket routing across Billing, Account and Technical queues. A user selects one of six scenarios, reviews a locally generated rule-based recommendation, optionally reveals its matched-keyword explanation and stated limitation, chooses a queue, and submits a decision. The reference answer is revealed only after submission. The user can then rate the explanation, add an issue tag or comment, inspect a session summary and export a local CSV record. The system is implemented in HTML, CSS and JavaScript with no external dependencies. A simple local keyword-scoring engine produces the recommendation; its displayed score is a heuristic, not a probability. No trained model is called and feedback does not change the rules. Records remain in the browser's local storage. The current scope is an interaction prototype for demonstrating visibility, user control, explanation access and feedback, not a validated experiment or operational support tool. It makes the decision process inspectable and provides a basis for later evaluation of perceived helpfulness against actual decision correctness.

## 1. Problem and project scope

Explainable AI (XAI) is often presented as a way to make machine-learning systems more transparent, but transparency alone does not guarantee better human decisions. Zhang, Liao and Bellamy (2020) found that confidence information could help calibrate trust without necessarily improving joint decision performance. Poursabzi-Sangdeh et al. (2021) likewise showed that making a model easier to simulate did not guarantee that people would detect and correct its mistakes. These findings motivate an interaction-focused prototype: can the interface help a user notice uncertainty, inspect a reason and challenge an AI recommendation?

ExplainCheck uses fictional support-ticket routing rather than a high-stakes domain. This bounded task provides a clear reference label and lets the interface show both correct and deliberately incorrect suggestions without implying clinical or operational validity. The prototype implements a complete interaction loop around a small keyword-based rule engine, which is explicitly labelled and is not a trained model.
## 2. Design rationale

A small, legible task. The three routing categories—Billing, Account and Technical—keep the choice understandable and make it possible to compare the AI label, user choice and reference answer. Six hand-authored scenarios include both matching and mismatching suggestions. This is a design probe, not a representative dataset: the difficulty labels and reference answers are illustrative and have not been validated with users.

Visibility of system status and honest score labels. The suggested category and a rule score are visible on the case card, labelled ‘Rule score · not a probability’. The engine assigns weighted points to matched keywords; the displayed score is a presentation aid, not a calibrated probability. This makes the limited inference process inspectable and avoids presenting a heuristic as a trained-model output. Zhang et al. (2020) make trust calibration relevant, but ExplainCheck cannot test calibration of a real model; it can only let a reviewer inspect the interface choice.

Progressive disclosure and limitations. Explanation details are hidden until the user selects ‘Reveal explanation’. The panel then shows short evidence cues and a limitation, instead of presenting a long technical account by default. This applies progressive disclosure and supports recognition over recall: the user can inspect specific cues at the moment of choice. A limitation is included because a reason can sound convincing while omitting decisive evidence. Rong et al. (2024) review user evaluations across trust, understanding, usability and human–AI performance, supporting the decision not to equate one positive user reaction with overall effectiveness.

User control and feedback. The user may accept or override the suggestion. The reference answer is withheld until after the decision so that the answer does not simply instruct the user what to choose. Afterward, a separate feedback form asks whether the explanation was helpful and allows optional issue tags and comments. This separates subjective usefulness from objective correctness. Smith-Renner et al. (2020) study the relationship between explanations, feedback and accountability in interactive machine learning; ExplainCheck therefore records feedback, but clearly states that the feedback is not used to retrain a model. Error recovery here means giving the user a visible route to report a problem, not claiming that the system has fixed it.

Evaluation beyond satisfaction. The session summary distinguishes user decisions matching the reference answer, AI suggestions that mismatch it, and cases where a user avoids a simulated AI error. These counters are descriptive rather than evidence of effectiveness: six fixed examples cannot establish general performance or causal impact. The interface follows usability heuristics such as visibility of system status, user control and clear feedback (Nielsen, 1994), but their success still needs to be checked through real walkthroughs and, later, a user study.
## 3. System architecture and illustrated interaction

The architecture is intentionally browser-only. HTML provides structure, CSS provides responsive layout and focus states, and JavaScript handles the case queue, keyword-scoring predictor, explanation cues, decision comparison, feedback form and export. The scenario bank, predictor and evaluator are separate modules. The predictor sums handcrafted keyword weights and returns a suggested queue, matched cues and a heuristic score; it does not learn from examples. `localStorage` retains the session on the same device, and a CSV can be exported. There is no server, external API, personal dataset or model-training pipeline. Figure 1 identifies the implemented components and features out of scope.

## 4. Development record, reflection and next step

The project was created from scratch as a new static application rather than adapted from the earlier full clinical-system repository. The main scope decision was to use a fictional, low-risk ticket task and avoid a trained model, login, database service or deployment dependency. This makes the prototype easier to run and inspect, while keeping the research question visible. Five automated unit tests check scenario completeness, rule-based predictions, decision evaluation, summary calculations and CSV escaping; they can be run with `npm test` and use Node's built-in test runner. No participant evaluation has been conducted, so the project makes no claim that the interface improves decision-making.

The most important limitation is that the rule explanations list matched keywords, while scenario limitations are manually authored; this is not a faithful explanation of a trained model. A next iteration would compare the current cue-based explanation with an alternative format, pilot the task with a small number of participants, and observe decision accuracy alongside perceived usefulness. Before such a study, the task and difficulty labels should be reviewed, the study procedure should be documented, and consent and data handling should be considered. The current contribution is a transparent and inspectable interaction prototype, not evidence of a validated XAI technique.
## 5. Conclusion

ExplainCheck operationalises a human-centred XAI question in a small, testable interaction: a person can inspect an AI-like recommendation, make an independent choice and provide feedback. Its central design principle is appropriate reliance rather than maximised trust. The next step is to validate the prototype and its measures, while keeping simulated behaviour clearly separated from real model output.
