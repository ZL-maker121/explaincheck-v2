# Technical reasoning and boundaries

- **Scenario bank:** six fictional, hand-authored tickets, illustrative reference queues, unvalidated difficulty labels.
- **Predictor:** `predictTicket(text)` lowercases text, finds each handcrafted substring, adds its weight to Billing/Account/Technical and selects the highest sum. Category order provides deterministic tie-breaking. Example EC-03: `{Billing: 6, Account: 7, Technical: 0}`, so Account wins by one raw point even though Billing is the scenario's reference answer.
- **Explanation:** presents only signals associated with the winning rules plus an authored limitation. It is not a local explanation generated by a trained model.
- **Decision control:** no radio option is preselected; submitting without a valid choice is rejected. The reference queue is shown only after an explicit choice.
- **Exposure distinction:** opening the explanation before commitment is stored as a boolean, and never inferred merely from receiving a feedback form. A usefulness rating is valid only if exposed beforehand; otherwise the feedback rating becomes `not-viewed`.
- **Persistence:** a local-only object is stored under `explaincheck-session-v2` in browser `localStorage`. No personally identifying information is required; never type real customer data.
- **Export:** user selection, reference label, raw points, exposure indicator, rating and comments are written to CSV locally. Comments are escaped for CSV; users should still treat the exported CSV as potentially unsafe if opened in spreadsheet software with untrusted user-entered formulas.
- **No backend:** no API credentials, network inference, server database, trained model, automatic feedback learning or validated user study.

## Architectural trade-offs

The static single-page approach runs without a build chain or network dependencies, making it inspectable. The rule engine is intentionally limited: it can show and explain a deterministic failure but cannot estimate general accuracy or test calibrated confidence. A future study would need more realistic, validated scenarios and independent participants, with consent and appropriate data handling.
